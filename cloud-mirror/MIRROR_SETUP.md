# First-phase mirror: concrete setup gate

Code is prepared in the existing companion; the original LifeOS is unchanged. This is **not live sync yet**. The owner approved read-only setup. The supported union reader was fixed and validated against real public collections: 45 tasks, 4 projects, 4 areas and 6 tags, including observed Logbook/Trash membership. No personal data was uploaded, no service credential was generated, and no LaunchAgent was installed. Secure user credential handoff remains blocked. Site MCP read access was verified by the parent; the cloud mirror remains empty. See [current secure handoff and supported coverage definition](mac/READ_ONLY_HANDOFF.md). Tests are our responsibility; Avi does not need to validate code, UI or routine sync runs.

## What is implemented

A one-shot stdlib Python helper runs fixed public AppleScript classification and JXA reads. It unions tasks/projects from all public lists, top-level collections and project/area children; areas/tags use their public collections. Returned cells preserve value/absence/unsupported/unknown separately, along with available relationships, timestamps and direct list membership/order. The AppleScript terminology is pinned to the verified app at `/Users/avi/Documents/apps/Things3.app`; moving/upgrading it requires checking that binding. It excludes private experimental scripting commands. [Field capability matrix](FIELD_CAPABILITIES.md) lists first-phase gaps. Checklists, headings, reminders, evening split, recurrence templates and full manual ordering are not claimed by this reader. No ThingsCloud or application database access occurs.

Snapshots are durably journaled before upload. Their manifest includes scope, count, IANA timezone, observation timestamp and SHA-256 hashes of all pages. Staged partial pages do not affect the confirmed cache; an atomic validated commit updates field revisions and scoped tombstones. Missing records mean absence from an exhaustive supported collection, not proof of physical deletion. Scope never includes unsupported headings. Omitted/unknown fields retain previous known data. Reused sequences and changed page content fail rather than overwrite. A lost helper journal requires reconciliation; do not reset/reuse its sequence.

Owner proposals carry the reviewed field revision and base value; approval matches an immutable hash. An approved operation remains a pending overlay until a supported Mac read verifies it. Only one title/notes field per task/project operation is prepared for phase-one writes. The helper persists intent, claims once, compares a fresh field read, attempts a narrow setter, then reads back and stores its receipt before acknowledgement. A crash without a receipt stays uncertain, even when a value happens to match; no blind write replay. Each operation has its own audit/outcome, so partial batches are honest. Unrelated fields are not replaced. Things has no cross-device atomic conditional write; an iPhone edit between check and setter can still race. Live writes stay disabled until this limitation and the scoped test are reviewed.

`planning_priority` is separate cloud-only metadata (`focus`, `normal`, `later`) and is never submitted to Things. The first phase does not claim to satisfy every internal field or give Things a numeric priority. Future tag-based prioritization needs a reviewed mapping.

## Exact one-time approval bundle

1. **Owner-private read/upload scope:** upload the supported task/project/area/tag IDs, kinds, titles, notes, direct tag IDs, parent IDs, status, available dates/timestamps and enumeration indices to the existing private Site `appgprj_6abce385ab0c8191b67a1d0808522bac`. Include open and closed records as returned by public collections. No Calendar fields; no unsupported internals. This creates a durable personal-data copy in Sites D1. Current safety ceilings are 10,000 records, 8 MiB per inventory, 100 upload pages and 240 KiB per page; exceeding a ceiling aborts without truncation or tombstones. Hosted backups/restore must be configured before treating this as the only copy; Things remains canonical.
2. **Service access:** authorize native creation of the private Sites dispatcher/bypass token and an independent random application sync key, plus owner-mediated secure configuration. The bypass is consumed by Sites and conveys **no human identity** or route-level scope. Therefore it cannot replace application authentication. Set `LIFEOS_SYNC_OWNER` from the trusted owner-signed-in mirror response, a fixed `LIFEOS_SYNC_ADAPTER` identifier, and `LIFEOS_SYNC_KEY_SHA256` in Sites secrets/environment, then set `LIFEOS_SYNC_ENABLED=true`. The helper sends the dispatcher token in `OAI-Sites-Authorization` and the separate key in `X-LifeOS-Sync-Key`. The Worker binds owner server-side and allows only begin/page/commit/pending/claim/ack. No machine approve/reject/propose/state route. Never enter tokens in chat, Git, command arguments, logs, plist or JSON configuration. The user enters the two values in their own secure Keychain UI under service `LifeOSMirror`, accounts `dispatcher` and `sync`; the agent does not echo or export them. There is no current service credential/configuration.
3. **Mac access and installation:** user-mediated macOS Automation grant for the chosen interpreter/helper to access Things, then install the prepared LaunchAgent and owner-only config/journal directory. Permission setup is required once, not validation on every sync. The sample config deliberately has both approvals false. Set read true only after the upload scope is approved; keep write false initially. Use a real installed Python absolute path and fill template placeholders, mode 0600 for config/journal and 0700 for their parent directory. No `KeepAlive`, shell endpoint, LLM process or new model subscription. Stop/unload `com.lifeos.mirror` to revoke background execution; rotate/revoke both credentials independently to revoke service access.
4. **Agent-run reversible test:** after step 1's read/upload approval, separately permit creating one clearly named disposable synthetic task through supported Things automation, changing/restoring only that fixture's title and notes through a reviewed proposal, checking Mac readback and duplicate/restart behavior, then trashing that disposable fixture (never empty Trash). Constrain the test writer to the fixture's exact ID. The full-inventory route still needs the explicit personal-data read/upload approval in step 1; fixture-test permission alone is not authorization to run a full personal inventory. No manual validation by Avi. Subsequent live title/notes writes require the reviewed phase-one policy and explicit owner edits; no routine per-sync confirmations. Other mutation kinds remain disabled.

Until these actions are approved, only fixture tests and disabled-service publication are allowed. Connecting dot/ChatGPT/Codex to the Site's plugin is also a separate user action; published MCP tools alone do not imply connection. The read mirror tool paginates; the draft tool proposes but cannot approve or execute. Human approval stays in an owner-authenticated surface under the existing proposal workflow.

## Background behavior and measurable budget

Prepared `mac/com.lifeos.mirror.plist.example` uses `RunAtLoad`, `StartCalendarInterval` at five-minute boundaries, background priority, restrictive umask and no persistent resident process. The local `launchd.plist(5)` manual confirms that calendar intervals missed while sleeping coalesce at wake (plain `StartInterval` does not). `--wake` allows one fresh pass, with a 30-second guard and no catch-up burst. Active network-failure backoff survives restart and is never bypassed by wake: 30 seconds doubling up to 3,600 seconds plus 0–20% jitter. Actual retries occur on the next five-minute launchd tick after the backoff expires; there is no resident 30-second retry loop. Each pass fetches at most 10 operations; the rest remain queued for later cycles. A single-instance file lock prevents overlap.

Target budget to measure during the approved live read test: Python helper RSS ≤50 MiB for a normal inventory; Python+temporary JXA combined RSS ≤100 MiB; average helper CPU ≤1% of one core over the five-minute interval; healthy pass normally ≤10 seconds. These are targets, not live measurements. Cooperative pass deadline is 90 seconds; a JXA subprocess times out at 45 seconds or remaining budget, and an HTTP request at 15 seconds or remaining budget. DNS/OS scheduling can exceed cooperative deadlines, so this is not a hard realtime guarantee. Idle resident CPU/RAM is zero because no helper process remains between intervals. The 8 MiB/count limits prevent silently escalating workload; exceeding them requires a design review, not truncation.

Successful/idle syncs emit no logs or notifications. The launch template does not surface routine diagnostics. Confirmed age, pending operations, true conflicts and uncertain receipts are visible in the cloud status. No notification delivery/monitor is configured; meaningful failure/conflict reporting through dot still needs its actual plugin connection. Persistent failure cannot be represented as success merely to keep things quiet.

## Verification commands

From companion root: `python3 -W error::ResourceWarning -m unittest discover -s tests -v` and `python3 -m compileall -q lifeos_cache tests`. Fixed JXA syntax can be compiled without executing: `/usr/bin/osacompile -l JavaScript -o /tmp/lifeos-things-read-syntax.scpt lifeos_cache/things_read.js`.
From `site/`: `node --test tests/runtime.test.mjs tests/mirror.test.mjs`, `node node_modules/typescript/bin/tsc --noEmit`, and the Sites bundled build/publish workflow. All tests use fixtures/local Miniflare; no real task read/write or credential is required. Published-host authentication, supported runtime reads, iPhone sync and performance are not established by fixture tests.
