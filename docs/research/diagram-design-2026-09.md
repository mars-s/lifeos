# Diagram Design for LifeOS meeting transcription

Research date: 2026-09-23

## Recommendation

Treat [diagram-design](https://github.com/cathrynlavery/diagram-design) as an optional diagram-authoring and export skill for polished meeting maps, not as the transcript processor or a replacement for the current Mermaid source format. It produces self-contained HTML with inline SVG, can redraw Mermaid input, and includes editorial layouts and accessibility checks. The repository exposes one shared skill package at `skills/diagram-design/`; its semantic patterns and type references are supporting materials loaded by that skill, not separate skills. [README](https://github.com/cathrynlavery/diagram-design#readme) · [Skill](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/SKILL.md)

The LifeOS skill inventory also contains an existing `meeting-debrief` skill. This note records only that inventory fact; its private instructions and meeting data are not reproduced here. The main agent should read that skill directly before applying it.

## Relevant skill and reference

1. **`diagram-design`** — The main skill fits when a visual will explain structure better than prose or a table. Before drawing, it requires checking the style-guide/profile gate, choosing a visual type (and semantic pattern when behavior is central), loading the selected type reference, and stating the type, size, and planned cuts before rendering. Its checklist requires an accessible SVG title/description, orthogonal connectors, a 4px structural grid, and a default budget of 9 nodes and 12 arrows; larger maps should be split into overview and detail. [Skill setup and selection](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/SKILL.md) · [Cookbook](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/docs/cookbook.md)

2. **`Unstructured input → structured artifact` semantic pattern** — This is the closest fit for turning a conversation into a reviewable meeting artifact. It requires showing representative source utterance(s), clarifying questions, extracted field/value pairs, the named transformation, the durable-artifact boundary, provenance links from representative statements, and missing/unknown values. Its limits are 4 exchanges, 6 artifact fields, one transformation, and 3 provenance links. The static fallback puts a short source excerpt beside the labeled artifact. The nearest visual layout is Data Flow (or Process if there are several ordered gates). [Semantic patterns](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/references/semantic-patterns.md)

For the actual relationship map, choose **Tree** only when each item has one parent and no backward/cross-links; it is capped at root plus 3 tiers and 5 children per level. Choose **Dependency Graph** only when shared parents or cycles are part of the story; it is capped at 9 nodes, 14 edges, 4 ranks, and one highlighted cycle. A meeting map with many-to-many connections may exceed these budgets and should become an overview plus focused detail, rather than a dense transcript-shaped hairball. [Tree reference](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/references/type-tree.md) · [Dependency Graph reference](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/references/type-dependency.md)

## Concrete integration constraints

- **Keep raw transcript processing upstream.** Inferred from the skill’s requirement to use representative excerpts and its small field/provenance budgets: derive a small, reviewable graph first, then give the diagram skill only that approved, minimized representation. Do not feed full transcripts or personal details to the diagram-generation step by default. Keep unresolved facts visibly unknown rather than inventing certainty. [Unstructured input pattern](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/references/semantic-patterns.md)
- **Keep generated output static by default.** The skill’s default is script-free static HTML; optional motion must use its reviewed controller, complete static fallback, and reduced-motion behavior. The README says motion output rejects arbitrary or modified inline scripts, remote assets, CSS imports, and executable HTML attributes. That is a meaningful limit for an interactive in-product canvas: use the static SVG as a rendered view, and keep interaction/data editing in LifeOS itself. [Skill](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/SKILL.md) · [README motion rules](https://github.com/cathrynlavery/diagram-design#semantic-patterns-and-optional-motion)
- **Check offline and privacy behavior before embedding.** The output is described as self-contained HTML/SVG with no build step or external image dependency, but the documented typography stack links Google Fonts. In a local-first meeting view, confirm whether generated HTML fetches fonts externally; bundle an approved font or use local/system fallbacks if a meeting view must make no third-party requests. [README output overview](https://github.com/cathrynlavery/diagram-design#what-it-makes) · [Skill typography](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/SKILL.md)
- **Preserve SVG accessibility when rendering inside LifeOS.** Each SVG needs `role="img"`, a resolving `aria-labelledby`, and prefixed `<title>`/`<desc>` IDs. If the app uses multiple diagrams or variants on one page, keep those IDs unique. [Skill checklist](https://raw.githubusercontent.com/cathrynlavery/diagram-design/main/skills/diagram-design/SKILL.md)
- **License:** the skill/repository declares MIT. Its third-party icon inventory includes MIT and CC0 sources and notes that brand marks remain their owners’ trademarks; retain applicable notices if bundling or redistributing those assets. ## Practical fit

The best trial is a **static, generated SVG/HTML view from a small reviewed meeting summary**, with Mermaid (if still useful as an editable source) retained upstream. It can improve presentation and accessibility for exported mind maps, but its strict node limits, default external font reference, and non-interactive output mean it should not own transcript ingestion, durable graph data, or the LifeOS interaction model.
