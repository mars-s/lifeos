# Memory systems for LifeOS

Checked against first-party repositories and documentation on 23 September 2026. The comparison began as a fit assessment; the Supermemory pilot is now installed and has passed a synthetic LifeOS end-to-end test.

LifeOS already saves exact brain dumps in SQLite, stores interpretations as immutable revisions, and can keep journal prose in Markdown. Its current search is lexical. Any memory engine should be a rebuildable index over those sources, meeting transcripts, and approved Things/Calendar records. Its returned claims need LifeOS source IDs and excerpts before ChatGPT presents them as evidence. See [the existing capture contract](../brain-dumps.md).

## Current decision

Use **Supermemory local first**, with its built-in ONNX embeddings and MiMo-V2.6-Flash for extraction through the user's OpenCode Go route. Keep the exact capture in LifeOS SQLite and journal prose in Markdown. Indexing is explicit and idempotent by capture ID. LifeOS stores a receipt and source links for extracted memories; Supermemory is a rebuildable search layer, not another authority for tasks, time, or journal text. Signet's source-attribution ideas inform the design without adding a second daemon. Hindsight is the next comparison only if Supermemory fails the source-fidelity and changing-facts tests. Graphiti and Cognee remain deferred.

The live synthetic test covered capture, indexing, extraction, status, and source-linked recall. It did not test private work material, long-term quality, deletion propagation, or laptop battery impact. OpenCode's [Go usage guidance](https://opencode.ai/docs/go/#where-can-i-use-it) still describes coding-agent traffic; technical compatibility does not settle whether this background workload is permitted.

## Recommendation

Start with **one** derived retrieval backend. Pilot Supermemory local against a small, fixed set of LifeOS sources because installation and API wiring are compact. Test five real questions: an exact meeting decision, a statement later reversed, a promise assigned to someone else, a journal-only recollection, and an answer that is absent. Require source excerpt, timestamp, source ID, and explicit uncertainty in every answer. Compare those same questions with Hindsight's `recall` if Supermemory cannot preserve the evidence or handle changes over time. Signet supplies the best design lessons for attributed claims and immutable evidence; importing its entire daemon would duplicate LifeOS's existing storage and approval logic.

Do not run two memory engines as independent authorities. If a second engine is compared, rebuild both from the same LifeOS records and evaluate outputs side by side. This keeps Things, Calendar, raw captures, and journal files authoritative and makes a later backend change reversible.

## Unverified before adoption

- The synthetic end-to-end test proved basic source linking, but not citation fidelity across real meetings, deletion propagation, changing facts, retrieval quality, or battery use.
- Supermemory's repository MIT license and local-server document cap describe different artifacts. Check the license presented by the actual binary/version before relying on its use terms.
- A hosted service sharing an API does not prove seamless migration of embeddings, graph state, IDs, or per-source permissions. Export/import paths need a pilot.
- Signet's current docs establish provenance and local operation; a general LifeOS app integration contract and hosted migration path remain to be verified.
